# Лабораторная 2

## Отрабатываемый материал

Явное межсервисное взаимодействие, gRPC

## Задание

Перенести service из 1 лабораторной в новый репозиторий
  
Расширить домен сервиса и перейти на gRPC API, реализовать HTTP гейтвей для него.

- расширить домен логикой инвойсов (invoice)
- реализовать gRPC API для сервиса банка
- добавить отдельное ASP.NET приложение переадресующее запросы – HTTP гейтвей
- HTTP гейтвей должен подключать клиент к gRPC сервису

## Сущности

Инвойс — запрос на оплату фиксированной суммы с одного счёта на другой. Инвойс содержит следующие данные:
- идентификатор
- номер счёта плательщика
- номер счёта получателя
- сумма
- статус (создан, оплачен, отозван)

Нельзя дважды оплатить один инвойс, нельзя оплатить отозванный инвойс

## Функциональные требования
Пользователь может:
- создать инвойс
- посмотреть исходящие инвойсы с фильтрацией по:
  - по номеру счёта плательщика
  - по статусу
- посмотреть входящие инвойсы с фильтрацией по:
  - по номеру счёта отправителя
  - по статусу
- оплатить инвойс
- отозвать инвойс

Оплата инвойса порождает 2 операции, как для плательщика, так и для отправителя.

## Нефункциональные требования
- использовать Itmo.Dev.Platform.Persistence.Abstractions в Application.Abstractions и Itmo.Dev.Platform.Persistence.Postgres в Infrastructure.Postgres в своих проектах
  - [документация](https://github.com/itmo-is-dev/platform/blob/master/docs/persistence.md)
- в таблице историй операций должна быть добавлена колонка payload типа jsonb, содержащая данные об операция (сумма, либо сумма и идентификатор инвойса в зависимости от операции)
  - должна присутствовать миграция, заполняющая новые данные для существующих строк истории
  - миграция для заполнения данных должна собирать json объекты, для этого стоит использовать функцию json_build_object, [документация](https://www.postgresql.org/docs/9.5/functions-json.html)
- все эндпоинты, возвращающие коллекции, должны быть реализованы при помощи пагинации с использованием page token
- модели gRPC API, подразумевающие полиморфизм, должны быть реализованы через `oneof` (элементы истории операций)
- HTTP гейтвей должен иметь Scalar/Swagger документацию, аннотированную
- все эндпоинты должны иметь описание возможных кодов в Swagger документации, а также описание возможных типов
  полиморфных моделей
- модели, подразумевающие полиморфизм, в API HTTP гейтвея должны быть реализованы **НЕ** в виде `oneof`
- должны быть реализованы серверные Interceptor-ы:
  - отдающий сообщения об ошибках в определённом формате
  - логирующий время исполнения операции (используя StopWatch)
- в HTTP гейтвее должен быть реализован middleware, для преобразования gRPC эксепшенов в конкретные HTTP коды
